# 校园跑腿平台 API 约定（V1）

> 本文作为前后端并行开发的共同约定。路径、字段和状态枚举一经组内确认，不要在单个模块中自行变更；需要调整时先更新本文并通知相关成员。
>
> 可导入 Apifox 的机器可读接口定义见[openapi.yaml](./openapi.yaml)。
>
> 前端调用与当前后端实现的差异、ID 类型基准及补齐优先级见[前后端接口差异与ID统一.md](./前后端接口差异与ID统一.md)。
>
> 五人职责边界、主流程配对和开发顺序见[分工边界与任务图.md](./分工边界与任务图.md)。

## 1. 总体约定

- API 前缀：`/api/v1`。
- 使用 JSON 请求和响应；字段名采用 `camelCase`。
- ID 由后端生成，在 JSON 中统一按字符串传递。服务端内部任务 ID 使用 UUID 字符串（数据库 `VARCHAR(36)`）；用户 ID 使用 `Long/BIGINT`，API 中仍序列化为字符串。取消申请、申诉、投诉和账务流水等独立资源可使用 UUID。
- 时间使用 ISO 8601 UTC 格式，例如 `2026-10-17T13:30:00Z`。
- 虚拟币使用整数。任务报酬是单一金额，不拆分跑腿费和小费。
- 当前用户身份从登录会话读取；请求体不接受前端传入的操作者 `userId` 或 `role`。
- 服务端必须检查登录状态、角色、任务参与关系和当前业务状态，不能依赖前端隐藏按钮来实现权限控制。
- 列表接口统一分页参数：`page` 从 `0` 开始，`size` 只接受 `10`、`20`、`50`，默认 `page=0&size=10`。
- 空列表是成功响应，返回空 `items`，不是错误。

## 2. 登录态与安全

本项目先采用 Spring Security 服务端 Session，避免首版同时引入 JWT、刷新令牌等复杂度。

- 登录成功后，服务端设置 Session Cookie；前端不得把会话凭证保存在业务数据或日志中。
- 注册只创建普通用户，自动建立登录会话，并在同一数据库事务中创建钱包、发放 100 虚拟币初始余额及写入初始入账流水；客户端不得指定角色或初始余额。
- 管理接口仅允许 `ADMIN` 角色访问。前端路由的角色判断只负责用户体验，后端必须再次鉴权；未登录返回 `401`，已登录但角色不足返回 `403`。
- 本地开发由 Vite 将 `/api` 代理到后端，减少跨域和 Cookie 配置问题。
- 写操作按 Spring Security 的 CSRF 保护要求携带 CSRF Token。
- 除 localhost 开发外，部署环境必须使用 HTTPS；生产 Cookie 应启用 `HttpOnly`、`Secure`。
- 密码不得明文保存或写入日志。

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/v1/auth/register` | 注册 |
| `POST` | `/api/v1/auth/login` | 登录 |
| `POST` | `/api/v1/auth/logout` | 退出登录 |
| `GET` | `/api/v1/auth/me` | 获取当前登录用户及角色 |
| `GET` | `/api/v1/auth/csrf` | 获取写操作所需的 CSRF Token |

个人资料与密码维护接口已实现。操作者身份均从登录会话读取，请求体不接受 `userId` 或 `role`：

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/v1/users/me/profile` | 查询本人资料、收到的任务评价均分与评价数，并返回预留的 `creditScore` 字段 |
| `PATCH` | `/api/v1/users/me` | 修改本人显示名和手机号；不能修改用户名或角色 |
| `POST` | `/api/v1/users/me/password` | 校验当前密码后修改本人密码 |

资料更新只允许修改 `displayName`（必填，1–50 个字符）和 `phone`（选填，最多 30 个字符，仅允许数字、空格、`+`、`-`；空白值清空手机号）。密码修改要求提供当前密码和新密码；新密码长度为 8–128，且不能与当前密码相同。当前密码错误返回 `400 VALIDATION_ERROR`。新密码以 BCrypt 哈希保存，不返回或记录明文密码。

`GET /api/v1/auth/me` 仍用于读取当前登录身份与角色；个人中心的完整资料和评价展示使用 `GET /api/v1/users/me/profile`。密码找回和连续登录失败锁定尚未实现。

## 3. 统一响应与错误

成功响应：

```json
{
  "code": "OK",
  "message": "success",
  "data": {
    "taskId": "generated-id"
  }
}
```

分页响应：

```json
{
  "code": "OK",
  "message": "success",
  "data": {
    "items": [],
    "page": 0,
    "size": 10,
    "total": 0
  }
}
```

错误响应：

```json
{
  "code": "TASK_STATE_CONFLICT",
  "message": "任务当前状态不允许此操作",
  "data": null
}
```

| HTTP 状态码 | 使用场景 |
|---|---|
| `200` | 查询或操作成功 |
| `201` | 创建成功 |
| `400` | 请求格式或参数错误 |
| `401` | 未登录或登录态失效 |
| `403` | 已登录但无权限 |
| `404` | 资源不存在，或当前用户不可见 |
| `409` | 状态冲突、并发抢单失败、余额不足或重复业务操作 |
| `500` | 未预期的服务端错误 |

错误码建议采用稳定的大写名称，例如 `VALIDATION_ERROR`、`TASK_NOT_FOUND`、`TASK_STATE_CONFLICT`、`INSUFFICIENT_BALANCE`、`DUPLICATE_ACTION`。前端根据 HTTP 状态码和 `code` 展示提示，不解析服务端堆栈。

## 4. 主要接口目录

### 4.1 用户、任务与钱包

| 方法 | 路径 | 主要用途 |
|---|---|---|
| `POST` | `/api/v1/tasks` | 发布任务 |
| `GET` | `/api/v1/tasks` | 浏览、筛选和分页查询任务 |
| `GET` | `/api/v1/tasks/{taskId}` | 查询任务详情 |
| `GET` | `/api/v1/users/me/tasks?as=publisher` | 查询本人发布的任务 |
| `GET` | `/api/v1/users/me/tasks?as=runner` | 查询本人接取的任务 |
| `PATCH` | `/api/v1/tasks/{taskId}` | 修改仍处于待接单状态的本人任务 |
| `POST` | `/api/v1/tasks/{taskId}/withdrawal` | 撤回尚未被接取的本人任务 |
| `POST` | `/api/v1/tasks/{taskId}/acceptance` | 接取任务 |
| `POST` | `/api/v1/tasks/{taskId}/delivery` | 跑腿员标记送达 |
| `POST` | `/api/v1/tasks/{taskId}/completion` | 发布者确认完成并结算 |
| `POST` | `/api/v1/tasks/{taskId}/reviews` | 提交任务评价 |
| `GET` | `/api/v1/wallet` | 查询本人余额 |
| `GET` | `/api/v1/wallet/transactions` | 查询本人虚拟币流水 |

发布任务请求示例：

```json
{
  "title": "代取资料",
  "description": "到教学楼领取资料并送到宿舍区",
  "reward": 30,
  "deadline": "2026-10-18T09:00:00Z",
  "pickupLocation": "教学楼A座",
  "deliveryLocation": "宿舍区"
}
```

接单请求不传接单人 ID；服务端从登录态确定跑腿员。并发接单时必须保证最多一个请求成功，其他请求返回 `409`，不得出现重复接单或重复扣款。

### 4.2 取消申请与已完成任务申诉

管理员列表查询和裁决接口要求当前会话角色为 `ADMIN`；普通登录用户不得通过直接调用 API 绕过管理端页面限制。

| 方法 | 路径 | 主要用途 |
|---|---|---|
| `POST` | `/api/v1/tasks/{taskId}/cancellation-requests` | 对进行中或待验收任务发起取消申请 |
| `POST` | `/api/v1/cancellation-requests/{requestId}/response` | 被申请方同意或拒绝取消 |
| `GET` | `/api/v1/admin/cancellation-requests?status=PENDING_ADMIN` | 管理员查询待裁决取消申请 |
| `POST` | `/api/v1/admin/cancellation-requests/{requestId}/arbitration` | 管理员裁决取消争议 |
| `POST` | `/api/v1/tasks/{taskId}/appeals` | 任务参与者对已完成任务提交申诉 |
| `GET` | `/api/v1/admin/appeals?status=PENDING` | 管理员查询待处理申诉 |
| `POST` | `/api/v1/admin/appeals/{appealId}/decision` | 管理员裁决申诉 |

取消申请应答示例：

```json
{
  "decision": "REJECT",
  "note": "补充说明"
}
```

申诉提交示例：

```json
{
  "reason": "FULFILLMENT_ISSUE",
  "description": "实际送达物品与约定不符"
}
```

申诉裁决示例：

```json
{
  "result": "PARTIALLY_SUPPORTED",
  "transferAmount": 10,
  "decisionNote": "根据双方提交的说明，部分支持"
}
```

申诉裁决必须满足以下规则：

1. 只有任务参与者可以对已完成任务申诉；同一参与者对同一任务最多提交一次。
2. 申诉裁决不改变任务“已完成”状态，也不修改原始结算流水。
3. 支持或部分支持时，从被申诉方可用余额向申诉人划转裁决金额；驳回时金额为 `0` 且不变更余额。
4. 余额检查、双方余额更新、申诉状态更新和双方关联申诉的流水写入必须在同一数据库事务中完成；任何一步失败均整体回滚。
5. 重复提交或重复裁决不得导致重复划转或生成重复流水。

### 4.3 通知与管理端

以下接口中，通知、投诉提交/处理留痕、管理员交易流水查询、管理员用户查询与系统通知发布已实现。操作日志查询尚未实现；投诉目前只保存有限处理留痕，不执行信用、账务或账号处罚。具体实现状态以[前后端接口差异与ID统一.md](./前后端接口差异与ID统一.md)为准。

| 方法 | 路径 | 主要用途 |
|---|---|---|
| `GET` | `/api/v1/notifications` | 查询本人通知 |
| `POST` | `/api/v1/notifications/{notificationId}/read` | 标记通知已读 |
| `POST` | `/api/v1/admin/notifications` | 管理员发布系统通知 |
| `POST` | `/api/v1/complaints` | 提交投诉 |
| `GET` | `/api/v1/admin/complaints` | 管理员查询投诉 |
| `POST` | `/api/v1/admin/complaints/{complaintId}/actions` | 管理员处理投诉 |
| `GET` | `/api/v1/admin/users` | 管理员查询用户 |
| `GET` | `/api/v1/admin/transactions` | 管理员查询交易记录 |
| `GET` | `/api/v1/admin/operation-logs` | 管理员查询操作日志 |

通知列表支持分页参数、`unreadOnly` 与 `type` 筛选；通知仅能由所属用户查询或标记已读。任务接单、送达、完成和评价等业务事件会生成 `TASK` 类型通知；管理员发布的系统通知为 `SYSTEM` 类型，不关联任务，前端据此区分展示。系统通知发布时，为当前全部已注册用户各写入一条通知并共用同一个发布时间；用户各自维护已读状态。

管理员用户查询支持可选的 `keyword`，按账号、显示名或手机号模糊匹配；结果按注册时间、用户编号倒序分页，只返回 `userId`、`username`、`displayName`、`role`、`phone`、`createdAt`，不暴露密码哈希。用户编号按字符串输出。

投诉与交易查询的补充约定：

- 投诉提交读取当前会话的投诉人身份。关联任务时必须是任务参与者；被投诉人只能是另一位参与者，省略时由服务端补全。没有关联任务时可提交一般问题，指定的被投诉用户必须存在，且不能是本人。
- 投诉列表可按 `status=PENDING|PROCESSED` 筛选，省略表示全部。响应补充 `reporterId`、`targetUserId`、`actions`、`decisionNote`、`handledBy`、`handledAt`，用于展示处理记录；所有 ID 按字符串输出。
- 本阶段只保存处理留痕，开放 `WARNING`（记录提醒与警告）、`LOG_ONLY`、`OFFLINE_REFERRAL`（记录线下移交）。提醒和线下移交需管理员另行完成，不自动发送通知或执行处罚。扣信用分、账务调整、功能限制和冻结账号尚未开放，对应动作或调整字段返回 `400 VALIDATION_ERROR`，投诉保持待处理。
- 处理需要至少一种不重复的已开放方式和 1—1000 字非空白说明。服务端以管理员会话记录操作者和时间，在事务中锁定投诉；重复或并发处理只允许一次成功，其余返回 `409 DUPLICATE_ACTION`，不覆盖原记录。
- 管理员交易流水查询支持可选的 `userId`、`taskId` 精确筛选，同时提供时取交集。`userId` 是正整数 BIGINT 编号的字符串；`taskId` 最长 36 字符。结果为所有用户的真实账本数据，不变更余额或流水。
- 两个管理列表均在数据库分页，先按 `createdAt` 倒序、再按资源 ID 倒序稳定排序。空结果及超出末页的查询返回成功和空 `items`，保留请求的 `page/size` 与真实 `total`；非法分页、状态或用户编号返回 `400 VALIDATION_ERROR`。

### 4.4 信用分规则（目标行为约定）

本节把需求分析中的信用分规则细化为实现口径；**信用分服务、查询接口、低分限制和投诉处罚目前尚未实现**。信用分与钱包虚拟币（任务报酬）相互独立，不得共用余额或交易流水。

#### 分值、档位与权限

- 新注册用户及首次启用本机制时已有的用户，信用分均初始化为 `80`。取值限制为 `0–100`，超出范围的变更按边界截断。
- 档位按当前分值确定：`90–100` 优秀、`75–89` 良好、`60–74` 预警、`0–59` 受限。
- `60–74` 用户仍可发布和接单；界面显示履约风险提示。任务列表查询条件相同时，预警档发布者的任务排在非预警档任务之后，组内继续使用现有排序。
- `<60` 用户不能接取普通待接单任务；其新发布任务进入管理员复核队列，不进入公开待接单列表。任务保留原有任务状态，并以独立的发布复核状态控制可见性。管理员批准后才公开；驳回后任务转为 `CANCELLED`，冻结报酬全额解冻。
- 分数恢复至 `75` 或以上时，系统自动解除低分限制并发送通知。未受限账号分值恰为 `60` 时不触发限制；已受限账号恢复到 `60–74` 时仍保持限制，恢复至 `75` 才解除。分数降到 `0` 时只提示管理员复核，不自动冻结登录账号；冻结账号须由管理员另行按投诉处理规则决定。
- 受限用户不能新接普通任务；已接取任务仍可完成并参与连续履约计数。若无在途任务，用户可对信用处分值发起复核，由管理员按“管理员复核调整”规则处理；不通过放开普通接单权限绕过受限规则。
- 他人查看个人主页时只返回信用档位和累计完成单数，不显示精确分数或变更明细；本人可查看精确分数、档位、权限说明、变更记录和恢复条件；管理员可查询全部用户的分值与记录。

#### 触发事件与分值变更

| 触发事件 | 对象 | 分值变动 | 判定与去重 |
|---|---|---:|---|
| 收到 5 星评价 | 被评价跑腿员 | `+2` | 评价成功保存后触发；每条评价只处理一次 |
| 收到 3–4 星评价 | 被评价跑腿员 | `0` | 只记零分值事件，不通知用户 |
| 收到 1–2 星评价 | 被评价跑腿员 | `-3` | 同一发布者对同一跑腿员的滚动 30 天内，只有第一次低星评价扣分；后续低星评价仍留零分值记录 |
| 按时完成任务 | 跑腿员 | `+1` | 任务最终完成且 `deliveredAt <= deadline` 时触发，每任务一次；不得与 5 星评价互相抵消或替代 |
| 超时送达 | 跑腿员 | `-5` | `deliveredAt > deadline + 24 小时` 时触发；未送达任务由管理员异常订单处理确认跑腿员负有责任后触发。每任务最多扣一次；截止时间至 24 小时之间不加分也不扣此项分 |
| 有责取消 | 被明确认定的责任方 | `-5` | 同意取消时由被申请方在应答中确认责任方；管理员裁决时明确选择责任方。责任值为 `REQUESTER`、`RESPONDER` 或 `NONE`，分别表示申请人、被申请人或双方无责。财务退款/支付比例不能推断责任方；`SUPPORT_CONTINUE` 必须为 `NONE` 且不产生取消扣分 |
| 投诉成立 | 被投诉方 | `-2 / -5 / -10` | 管理员根据轻微/一般/严重情节选择一档；每条投诉最多扣一次。仅提交举报、投诉待处理、投诉驳回或 `targetUserId` 为空的任务内容举报均不扣分 |
| 连续履约恢复 | 跑腿员 | 恢复至 `75` | 连续完成 10 个任务且期间没有负向信用事件后触发；只在当前分数低于 75 时补至 75，不把更高分降至 75。取消任务不计入完成单；任何负向信用事件都会将连续计数清零 |
| 管理员复核调整 | 被复核用户 | 管理员指定整数 | 必须填写复核说明；调整后仍截断在 `0–100`。保留原记录并追加调整记录，不覆盖或删除历史 |

信用分的每条变更记录至少包含记录 ID、用户 ID、触发事件类型及 ID、原因、请求变动值、实际变动值、变更前后分值、发生时间；管理员操作另记录管理员 ID。首次启用时已有用户统一初始化为 `80`，并写入 `INITIALIZATION` 基线记录（变更前分数为空，变更后为 `80`，变动值为 `0`）。账面分数变化和记录写入必须在同一信用分事务中成功或失败。信用分事件以业务资源 ID 幂等，同一任务评价、取消申请、超时判定或投诉不得重复记分。实际变动值为 `0` 的事件可留痕，但不发送分值变化通知。

投诉扣分档位按以下口径选择：`-2` 为一次、轻微且无实质损失的违规；`-5` 为一般违约、重复不履约或造成可说明的实际影响；`-10` 为有证据支持的故意欺诈、重大财物损毁或人身安全风险。投诉分类本身不能自动决定档位，管理员须在处理说明中记录事实依据。达到严重情节不代表自动冻结账号，冻结仍须作为独立管理动作处理。投诉复核若推翻原结论，以新的反向信用记录纠正，禁止删除原扣分记录。

信用分变更成功后，非零分值变化通知用户，档位或限制状态变化也通知用户；零分值留痕不通知。连续履约恢复发出的通知须说明恢复结果和限制状态。

为遵守“信用分记录失败不回滚已完成业务操作”的需求，业务事务应可靠记录待处理的信用分事件；信用分消费者独立更新分值和变更记录，失败时保留事件并重试，不能静默丢弃。待处理事件按源事件 ID 幂等处理。

**实现边界**：`<60` 用户新发布任务的复核队列、管理员对异常任务的超时责任确认、取消责任方字段、投诉信用扣分/复核、信用分事件重试及信用分查询接口，均须在实现阶段增加对应契约与持久化支持；不能仅靠前端按钮禁用或从报酬分配比例猜测责任。

#### 前端 B 信用对接契约 待后端确认

新增信用分查询、管理员调整、投诉扣分复核与本人复核申请的机器可读草案见 [openapi-credit.draft.yaml](./openapi-credit.draft.yaml)。草案不是已实现的后端接口；前端按草案发起真实请求，读取失败显示错误，不回退为初始 80 分或模拟记录。当前后端仍只支持投诉处理留痕。个人中心和他人主页的信用展示由前端 A 接入，本阶段不改其页面。

投诉处理沿用 `POST /admin/complaints/{complaintId}/actions`。后端 B 在投诉 DTO 中补充 `allowedActions`：只有明确包含 `CREDIT_ADJUSTMENT`、投诉仍待处理且 `targetUserId` 非空，前端才开放扣分。新增 `complaintResult=SUPPORTED|REJECTED`，扣分时必须为 `SUPPORTED`，`creditAdjustment` 只能为 `-2/-5/-10`，且 `decisionNote` 必须记录事实依据。任务内容举报、驳回投诉和未指定被投诉用户的记录不可扣分。旧的留痕请求保持原有字段，不因信用接口未上线而失效。

扣分回执在现有投诉 DTO 中增加 `creditStatus=PENDING|APPLIED|FAILED`、`creditAdjustment`、`creditActualAdjustment` 和 `creditRecordId`；实际扣分与请求值分开显示，避免边界截断后误报。只有 `creditStatus=APPLIED`、原信用记录存在且 `creditReviewAllowed=true` 时开放投诉扣分复核；复核记录由后端追加，撤销按原记录实际扣分纠正。待处理或失败的信用事件不能展示为已生效。

信用摘要同时返回分数、档位与明确的权限标志。前端以 `restrictionActive`、`canAcceptNormalTasks`、`requiresPublishReview` 展示接单限制和发布复核提示，不从 60–74 的档位自行推断是否已解除历史限制；后端应在恢复至 75 时解除限制。未知或读取失败的信用状态不显示为正常或受限，现有业务请求仍由后端最终鉴权。受限账号已接取任务的送达、验收等履约入口不受新接单限制影响。

新增信用写操作使用 `Idempotency-Key`；同一次提交在超时后重试保留键，修改内容或目标后换键。管理端支持用户编号、档位及待复核筛选、变更记录分页，统一 `page=0`、`size=10/20/50`。后端必须独立完成 ADMIN 鉴权、状态和权限检查、幂等与审计；前端提供的按钮状态不是安全边界。后端 A/B 确认路径和字段后再将草案合入主 OpenAPI，并完成真实数据库联调。

发布复核使用独立的可选 `Task.publicationReviewStatus=NOT_REQUIRED|PENDING|APPROVED|REJECTED`，不扩充既有五种任务状态。发布响应为 `PENDING` 时前端提示“已提交复核”并进入本人任务详情，不引导用户到公开列表查找该任务；后端 B 负责公开列表过滤、参与者详情可见性和复核状态的真实性。

### 当前实现范围与未实现项

- 已实现的用户端能力包括注册/登录/退出、当前用户查询、个人资料查看与编辑、登录密码修改、任务发布/浏览/修改/撤回/接单/送达/验收/评价、对任务内容举报、钱包流水、通知（任务通知与系统通知）、取消申请与应答、管理员取消裁决及已完成任务申诉裁决。
- 已实现的本阶段管理端能力包括投诉提交与处理留痕、管理员交易流水查询、管理员用户查询、系统通知发布、取消争议与申诉列表/裁决。投诉处理目前只开放 `WARNING`、`LOG_ONLY`、`OFFLINE_REFERRAL` 的记录；不会自动发送提醒或执行处罚。
- 异常订单处理、专用管理员任务筛选、全系统操作日志查询，以及信用分规则/限制和投诉处罚尚未实现。信用分的目标规则见本节；规则写入文档不代表接口或后端行为已经交付。
- 密码找回和连续登录失败锁定尚未实现；`creditScore` 目前仅为资料响应中的预留字段，恒为 `null`，不代表已有信用分计算或限制机制。变更实现范围时应同步更新 OpenAPI、本文和接口差异盘点。

## 5. 状态枚举

接口上传递稳定的大写英文枚举；中文仅用于文档和界面显示。

任务状态只能是以下五种：

| API 值 | 界面显示 |
|---|---|
| `WAITING_FOR_TAKER` | 待接单 |
| `IN_PROGRESS` | 进行中 |
| `WAITING_FOR_ACCEPTANCE` | 待验收 |
| `COMPLETED` | 已完成 |
| `CANCELLED` | 已取消 |

取消申请状态：

| API 值 | 界面显示 |
|---|---|
| `PENDING_RESPONSE` | 待应答 |
| `PENDING_ADMIN` | 待管理员处理 |
| `APPROVED` | 已同意 |
| `ARBITRATED` | 已裁决 |

已完成任务申诉状态：

| API 值 | 界面显示 |
|---|---|
| `PENDING` | 待处理 |
| `DECIDED` | 已裁决 |

不提供允许客户端任意修改任务状态的通用接口；只能调用接单、送达、验收、取消等明确的业务操作。

## 6. 账务、事务与并发约定

- 发布任务冻结报酬、完成任务结算、取消裁决和申诉划转时，余额变更与交易流水必须在同一数据库事务中提交或回滚。
- 不提供前端直接修改余额的接口；余额只由明确的业务操作变更。
- 服务端每次执行写操作时重新读取并校验最新状态，不信任页面中缓存的状态。
- 接单使用事务内条件更新或等效并发控制，保证同一任务只能被一人接取。
- 重复请求不得重复扣款、入账、退款或划转；对于可能因网络重试重复提交的操作，后端应通过状态约束和业务唯一性保证幂等。
- 错误要显式返回稳定错误码，不要吞掉异常或用成功响应包装失败。

## 7. 第一条端到端验收路径

按顺序使用两个普通账号完成以下流程，并检查任务状态、余额与流水：

1. 注册并登录。
2. 账号 A 发布任务并确认报酬被冻结。
3. 账号 B 接取任务。
4. 账号 B 标记送达。
5. 账号 A 确认完成。
6. 账号 B 确认收到结算，双方查看对应流水。

主流程稳定后，再验收取消申请/管理员裁决、已完成任务申诉/管理员裁决，以及并发接单、重复请求、余额不足和事务失败等情况。
